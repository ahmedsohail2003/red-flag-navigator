## Missing or contradicted

- Free Sensor Logger is not a real-time controller path. Its HTTP/MQTT push sends 1-second batches unless you pay (row 9). For a Wii-remote-style watch controller with no Apple-side coding, TDInput (50 Hz OSC through the iPhone) is the only ready-made option found; use Sensor Logger, Care Sensors or SensorLog for recording.
- Windows 11 receiver gotcha the notes miss: Windows Firewall blocks inbound traffic by default. The first time your receiver (for example python.exe listening on UDP 9000 for TDInput, or an HTTP port for Sensor Logger) opens a port, Windows prompts, and cancelling the prompt creates block rules. Add an inbound allow rule for that port on the Private profile (`New-NetFirewallRule`), set the Wi-Fi network to Private, and allow Local Network access for the relay app on the iPhone. Sources: https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules (updated 2026-10-08); https://learn.microsoft.com/powershell/module/netsecurity/new-netfirewallrule
- The notes' Q2 takeaway overstates the papers: "research pipelines that relay watch IMU via the iPhone run at 25-30 Hz". Only IMUPoser documents an iPhone relay, and its 25 Hz cap came from the AirPods, not from the watch link. ArmPoser's 30 Hz path is unstated. Neither paper measures how fast WatchConnectivity can go, so no published number limits a 50-100 Hz batched watch stream. Measure it yourself.
- Every live path from an Apple Watch to Windows goes through an iPhone app over Wi-Fi (or through an internet HTTPS server). Apple Watch needs an iPhone (iPhone 11 or SE 2nd gen or later with iOS 27 for watchOS 27). It cannot pair with Android or with Windows directly.
- Code check: Apple's own raw-gyroscope sample on "Getting raw gyroscope events" uses `RunLoop.current.add(self.timer!, forMode: .defaultRunLoopMode)`. That is the old Swift 4.0/4.1 spelling. Current Swift calls it `.default` (`RunLoop.Mode.default`; swift-corelibs-foundation defines only `default` and `common`), so change that line before compiling. On watches where `isGyroAvailable` is false the sample delivers no data anyway. For the watch, use `startDeviceMotionUpdates(to:withHandler:)` and read `rotationRate`. - For question 3 (BioHacks ALS phone walking test), the notes miss ResearchKit. It is open source (release 3.4.2, 2026-09-23) and already has iPhone "Timed Walk" and "Gait and Balance" active tasks that record accelerometer, device motion and pedometer data. Timed Walk "measures the user's lower-extremity function". It is the closest ready-made base for that test. `CMPedometer` `currentCadence` (iOS 9+, watchOS 2+) gives live steps per second. These are research tools, not validated ALS measures. Sources: https://github.com/ResearchKit/ResearchKit ; https://developer.apple.com/documentation/coremotion/cmpedometerdata/currentcadence
- Do not build on undocumented 27.0 additions: `CMRecordedDeviceMotion` (header only: passively recorded device motion, including headphones) and SensorKit's new `SRAccelerometerSensor` / `SRRotationRateSensor` structs have no documentation beyond their names. WWDC26's "watchOS Group Lab" (session 8014) only speculated that a watch "could" act as a motion peripheral for visionOS. No new watch motion or networking API was announced.
- Relevant to the AirPods question: IMUPoser (2023) measured AirPods head motion at about 25 Hz, the slowest device in its setup. Apple's Core Motion change log (June 2024) says `CMHeadphoneMotionManager` can read AirPods device motion on watchOS too, so a watch app could read AirPods head tracking.
