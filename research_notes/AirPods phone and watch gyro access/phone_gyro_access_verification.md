## Missing or contradicted

- **Scope.** This file covers phones only. The report's other questions (Hack the North 2026 winners and the AirPods project, Apple Watch, Fitbit, ALS walking test, Wii-remote bridging) are in the sibling notes in this folder (`htn_2026_results.md`, `htn_airpods_project.md`, `airpods_motion_api.md`, `apple_watch_gyro.md`, `fitbit_gyro.md`, `motor_test_applications.md`, `wii_remote_bridge.md`) and their own verification files. Nothing here settles the Hack the North questions.
- **Internal contradiction fixed.** The notes say both that every iPhone browser follows Safari's tap-to-request rule and that WKWebView has no `requestPermission()`. The second is wrong for current WebKit (see the refuted row). Any WKWebView app linked against the iOS 13 SDK or later exposes it and prompts by default.
- **iOS 27.2 has shipped (26 Oct 2026).** The notes still call it a beta. The new `CMMotionManager.authorizationStatus` is live. Press reports link it to a China-only "Restrict Motion Data" setting (Settings > Privacy & Security > Motion & Fitness). Apple has not documented it, so native code and no-code apps should be ready for a denied status.
- **Chrome default closed.** The gap "has Chrome flipped motion sensors to Ask?" is answered: no. Chromium main still registers SENSORS with a default of ALLOW (2026-11-07).
- **Safari mixed content may change.** WebKit main now has Local Network Access mixed-content exemptions for local IP targets (commit 2026-09-04). They sit behind an off-by-default "unstable" flag, so today's advice (serve page and socket from one HTTPS origin) stands. Watch for the flag to ship.
- **Pythonista is a second no-Mac iPhone route.** Pythonista 3 ($9.99) runs Python with a `motion` module on the iPhone, which suits a Python-first user. Its documented module has no rotation-rate getter and no stated rate.
- **AirPods and Watch through a phone app, no code.** The notes do not say this plainly: Sensor Logger's HTTP and MQTT push includes `"headphone"` readings (AirPods attitude, rotation rate, gravity, acceleration, left or right) and `"wrist motion"` readings (Apple Watch) in the same JSON schema. That is the quickest way to get AirPods or Watch motion to a Windows laptop without a Mac, but it needs an iPhone. `CMHeadphoneMotionManager` is iOS 14+ and macOS 14+, and Apple warns the app crashes if `NSMotionUsageDescription` is missing (Apple docs, fetched 2026-11-07).
- **SensorLog on Apple Watch (App Store, fetched 2026-11-07).** Background logging of all sensors runs at up to 50 Hz and single sensors at up to 100 Hz. HTTP sending from the Watch is capped at 10 Hz. This is useful for the Watch question but missing from the notes.
- **Motor-test building blocks the notes miss (for question 3).** HealthKit already computes mobility metrics on iPhone and Watch: `sixMinuteWalkTestDistance`, `walkingSpeed` and `walkingAsymmetryPercentage` (iOS 14+, watchOS 7+), and `appleWalkingSteadinessEvent` (iOS 15+). `CMMovementDisorderManager` (watchOS 5+) records tremor and dyskinesia, but "requires an entitlement from Apple". Both need a native app, so on Windows that means Expo with a config plugin or a cloud Mac build. A phone walking test can use the raw-sensor routes in the notes instead. Gait events are low-frequency, so the 60 Hz web route is probably enough (inference, not checked against a gait study here).
- **Expo Go and Local Network privacy (inference from TN3179).** Expo Go makes outgoing connections to the laptop's Metro server and any WebSocket on the LAN, so iOS shows the Local Network prompt. If the user denies it, both the dev connection and the sensor stream fail until it is re-enabled in Settings > Privacy & Security > Local Network. phyphox, as a server on the phone, should not trigger the prompt (TN3179: accepting incoming TCP is exempt).
- **Still unverified (no primary source found).** These items need a test before the event: WebSockets over trycloudflare quick tunnels; localhost.run WebSocket support and URL lifetime (its docs page refused the fetch); `wss://` to a self-signed certificate on iOS 26/27; real delivered `devicemotion` rates on 120 Hz ProMotion iPhones; Safari's `event.interval` value on a real device; Windows Defender Firewall's behaviour on a "Public" hotspot profile (no Microsoft document was fetched).
- **Minor.** The notes' Android stable figure (157.0.8103.47) is right, but chromiumdash also lists an early-stable 158.0.8127.22 on 2026-11-04. M158's full stable date is 2026-11-17. The SensorServer README's own USB example has a stray colon (`ws://localhost:8081:/...`); use `ws://localhost:8081/sensor/connect?type=...`.
