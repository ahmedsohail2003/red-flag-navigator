## Missing or contradicted

- **Fitbit Web API is already off, and Google's own pages give different dates.** dev.fitbit.com says support ended September 30, 2026 and "On October 30, 2026, the Fitbit Web API will be turned off". The Google Health newsletters page says "On November 2, 2026, the legacy Fitbit Web API and Fitbit OAuth endpoints will be turned off". That page's August 2026 issue said the API "will be turned down" on September 30, 2026. All three dates are before 2026-11-07, so new Fitbit work must use the Google Health API. The motor notes' only Fitbit evidence (Jewett 2026) used the old Web API and only steps and heart rate. Neither the Web API nor Health Connect exposes raw gyroscope or accelerometer data. The notes do not explain how to get raw motion from a Fitbit at all; see `fitbit_gyro.md`. Sources: https://dev.fitbit.com/build/reference/web-api/ ; https://developers.google.com/health/newsletters
- **Browser motion timing (rows 1-2).** iOS Safari reports `event.interval` in seconds (about 0.0167), Chrome reports 16 and Firefox reports 100. Both Chromium and WebKit poll the latest sample on a 60 Hz timer. `event.timeStamp` is set when the event is dispatched, not when the sensor sampled, and sensor hiccups show up as repeated values. This adds timing error on top of the clean 60 Hz grid the notes simulated (AUC 0.83). The worst case is about one frame (16.7 ms) per event; the typical size has not been measured, so log `event.timeStamp` and repeated values on the actual test phones. A native app gets true sample timestamps (Core Motion sample timestamps or Android `SensorEvent.timestamp`).
- **Secure context matters for development on Windows.** `DeviceMotionEvent` is `[SecureContext]` in both engines. A phone that loads the dev server from the Windows laptop at `http://192.168.x.x:port` receives no motion events. Options: an HTTPS tunnel, a locally trusted certificate, or (Android only) Chrome USB port forwarding, so that the page is served as `localhost` on the phone.
- **Real-time streaming to a laptop is not covered in this note.** Relevant constraints found here: `CMBatchedSensorManager` delivers one batch per second and only during a HealthKit workout session, so Apple Watch high-rate data arrives with at least about 1 s of latency. AirPods give about 25 Hz from one bud at a time, with data loss.
- **AirPods practical settings.** The TWSCardio measurements say sample loss is worst in ANC and Transparency modes and at a distance from the phone (row 5). The notes' "AirPods-like" 25 Hz simulation includes rounding of event times only, not sample loss, so it is optimistic for AirPods. No study validates AirPods stride timing; the notes' gap statement stands.
- **Placement ranking (row 12).** The notes' order, with the bag last, contradicts the source it cites. Keep belt or body-fixed first, and do not present the rest of the order as published.
- **WatchALS phone position (row 10).** The paper most likely used a lower-back belt for the walk too, which supports the notes' advice to use a belt clip. The notes describe the fine-motor improvement as "practice-related". The paper reports improvement in both groups and names "learning effects" as a possible cause, but does not show that practice caused it.
- **Manor error magnitude (row 11).** The correlation is r² = .98. The 16.9 ms figure is a mean per-stride error magnitude, as the notes' own inference already says, not a jitter SD.
- **Firefox and Samsung Internet (a gap the notes list).** Firefox for Android requests motion sensors at 60 Hz but reports `interval` as 100 and combines events in its own way (`nsDeviceSensors::FireDOMMotionEvent`). Samsung Internet is built on Chromium, so it should follow rows 1-2, but that was not checked on a device.
- **Apple Watch model support.** "Series 8 and Ultra" for 800 Hz / 200 Hz is the June 2023 statement. Apple's current reference lists no models. Check support at run time rather than assuming newer watches are excluded or included.
- **Out of scope here.** This note does not address question 1 (Hack the North 2026 winners and the AirPods controller team). See `htn_2026_results.md`, `htn_airpods_project.md` and their verification files.
