# Reading phone gyroscope and accelerometer data and streaming it to a laptop in real time (iPhone and Android, as of 2026-11-07)

Notes compiled 2026-11-07. Many facts were checked directly in browser or app source code or in official docs fetched on 2026-11-07; those are marked "(source code, read 2026-11-07)". Source dates are given where the source shows one. Context for the reader: the user develops on Windows 11 and may not have a Mac.

## Web route: what devicemotion / deviceorientation give on iOS Safari and Android Chrome, how requestPermission works, HTTPS and self-signed certificates, and the Generic Sensor API

### Takeaway
Both mobile browsers expose the same W3C fields (acceleration in m/s², rotationRate in deg/s, orientation angles in degrees) at about 60 Hz, and only in a secure context (HTTPS, or http://localhost). On iPhone the page must call `DeviceMotionEvent.requestPermission()` (and `DeviceOrientationEvent.requestPermission()`) from a tap. Chrome added the same methods in M151/M152 (mid-2026), but by default they still return "granted" without a prompt. The Generic Sensor API (`Gyroscope`, `AbsoluteOrientationSensor`) works only in Chromium browsers (Android Chrome, capped at 60 Hz), not on iOS. An HTTPS page with a self-signed certificate that the user clicked through is still a secure context (by spec and WebKit code), but `wss://` to a self-signed server is unreliable on iOS. A publicly trusted certificate, for example from a tunnel, avoids all of this.

### Cited Findings

**Spec status, fields and units**
- The W3C "Device Orientation and Motion" spec is a Candidate Recommendation Draft dated 26 October 2026 (previous draft 12 Feb 2025), published by the Devices and Sensors WG and the Web Applications WG — [W3C TR orientation-event (CRD 2026-10-26)](https://www.w3.org/TR/orientation-event/)
- deviceorientation: alpha (about z) in [0, 360), beta (about x') in [-180, 180), gamma (about y'') in [-90, 90), in degrees, as intrinsic Tait-Bryan Z-X'-Y'' angles. Each angle's "precision" is limited "to 0.1 degrees". The spec notes alpha "is in the opposite sense to a compass heading" — [W3C TR](https://www.w3.org/TR/orientation-event/)
- deviceorientation fires on a "significant change"; when that happens is "implementation-defined, though a maximum threshold for change of 1 degree is recommended" — [W3C TR](https://www.w3.org/TR/orientation-event/)
- devicemotion: `acceleration` and `accelerationIncludingGravity` (x, y, z in m/s²); `rotationRate` alpha/beta/gamma "measured in degrees per second (deg/s)" with the right-hand rule; `interval` "must be expressed in milliseconds (ms)" and is constant — [W3C TR](https://www.w3.org/TR/orientation-event/)
- Spec example: a device lying flat, screen up, has acceleration of zero and `accelerationIncludingGravity` `{x: 0, y: 0, z: 9.8}`. In free fall, `acceleration` is `{0, 0, -9.8}` — [W3C TR](https://www.w3.org/TR/orientation-event/)
- The spec sets no sampling-rate number: "Further implementation experience is being gathered to inform the limit for the maximum sampling frequency cap." The Permissions integration is marked "at risk" — [W3C TR](https://www.w3.org/TR/orientation-event/)
- MDN (DeviceMotionEvent page, last modified 4 Aug 2026) gives the same units (m/s², degrees per second, ms) and warns that Firefox and Chrome do not handle the coordinates the same way — [MDN DeviceMotionEvent](https://developer.mozilla.org/en-US/docs/Web/API/DeviceMotionEvent)

**Actual rates and values: Chrome (Android)**
- Chromium's device-motion/orientation event pump has `kDefaultPumpFrequencyHz = 60`. Gyroscope readings are converted with `base::RadToDeg`, and `interval` is set to `kDefaultPumpDelayMicroseconds / 1000` (an integer division, giving 16 ms) — (source code, read 2026-11-07) [device_sensor_event_pump.h](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/device_orientation/device_sensor_event_pump.h), [device_motion_event_pump.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/device_orientation/device_motion_event_pump.cc)
- Android's own accelerometer reports +9.81 on z when the phone lies flat (spec-conformant). A 2014 W3C thread reported Android as `{x:0, y:0, z:9.81}` and iOS as `{x:0, y:0, z:-9.81}`. A reply said "iOS and Chrome Android have exactly opposite readings for X,Y and Z (very annoying)" — [public-geolocation, Oct/Nov 2014](https://lists.w3.org/Archives/Public/public-geolocation/2014Oct/0022.html)

**Actual rates and values: Safari / WebKit (iOS)**
- WebKit on iOS drives CoreMotion with `kMotionUpdateInterval = 1.0f / 60.0f` (60 Hz). It uses `startDeviceMotionUpdates` when `deviceMotionAvailable`, otherwise accelerometer-only updates — (source code, read 2026-11-07) [WebCoreMotionManager.h](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ios/WebCoreMotionManager.h), [WebCoreMotionManager.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ios/WebCoreMotionManager.mm)
- WebKit computes `acceleration = userAcceleration × 9.80665` and `accelerationIncludingGravity = (userAcceleration + gravity) × 9.80665`, and converts rotationRate with `rad2deg`. It does not flip any sign — (source code) [WebCoreMotionManager.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ios/WebCoreMotionManager.mm)
- WebKit passes `kMotionUpdateInterval` (1/60, a value in seconds) unchanged into `DeviceMotionData`, and `DeviceMotionEvent::interval()` returns it as is — (source code) [DeviceMotionClientIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ios/DeviceMotionClientIOS.mm), [DeviceMotionEvent.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/DeviceMotionEvent.cpp)
- Native iOS apps can get more: Apple says CoreMotion's maximum rate "is hardware-dependent but is usually at least 100 Hz" — [Apple: Getting raw accelerometer events](https://developer.apple.com/documentation/coremotion/getting-raw-accelerometer-events)

**requestPermission(): iOS Safari behaviour**
- MDN (last modified 4 Aug 2026): "This method requires transient activation, meaning that it must be triggered by a UI event such as a button click." It returns "A Promise that resolves with a string which is either "granted" or "denied"." It rejects with `NotAllowedError` when "The permission state is "prompt" and the calling function does not have transient activation." It is secure-context only and "not Baseline" — [MDN requestPermission()](https://developer.mozilla.org/en-US/docs/Web/API/DeviceMotionEvent/requestPermission_static)
- Spec algorithm: `DeviceMotionEvent.requestPermission()` asks for "accelerometer" and "gyroscope". `DeviceOrientationEvent.requestPermission(absolute)` also asks for "magnetometer" when absolute is true. A "prompt" state without transient activation rejects with NotAllowedError; a refusal resolves "denied" — [W3C TR](https://www.w3.org/TR/orientation-event/)
- WebKit implementation (source code, read 2026-11-07):
  - If the browsing context is not secure, `requestPermission()` resolves "denied" and logs "Call to requestPermission() failed, reason: Browsing context is not secure."
  - Third-party iframes are refused unless the Permissions Policy allows gyroscope and accelerometer.
  - If the state is still Prompt and there is no user gesture, the promise rejects with NotAllowedError "Requesting device motion access requires a user gesture to prompt".
  - [DeviceMotionEvent.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/DeviceMotionEvent.cpp), [LocalDOMWindow.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/LocalDOMWindow.cpp)
- WebKit stores each decision per top-level (main-frame) origin. In the UI process the store is an in-memory map, `m_deviceOrientationPermissionDecisions`, inside the WebsiteDataStore. A cached Granted or Denied is returned without prompting again. When permission is granted, every frame starts listening for orientation and motion — (source code) [WebDeviceOrientationAndMotionAccessController.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebsiteData/WebDeviceOrientationAndMotionAccessController.cpp), [DeviceOrientationAndMotionAccessController.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/DeviceOrientationAndMotionAccessController.cpp)
- Developer reports say Safari caches the answer across reloads, and that some users get "denied" immediately with no pop-up (iOS 16.3 and 16.6). One site's help text suggests clearing that site's data in Safari settings and reloading — [Apple Developer Forums 128376](https://developer.apple.com/forums/thread/128376), [Defold forum](https://forum.defold.com/t/how-to-force-safari-browser-to-allow-deviceorientation-permission-solved/75641) (found via search; I did not open them)
- A WebKit bug reports that calling requestPermission after a round trip to a Web Worker (postMessage) loses the user gesture, and the request is denied — WebKit Bugzilla, found via search ([bug 269706](https://bugs.webkit.org/show_bug.cgi?id=269706), not opened)
- The global Safari "Motion & Orientation Access" setting is reportedly gone since iOS 13 ([Apple Community 254886785](https://discussions.apple.com/thread/254886785)). However, Expo's docs (SDK 58) still say iOS users "may have Motion & Orientation Access disabled" ([Expo Gyroscope docs](https://docs.expo.dev/versions/latest/sdk/gyroscope/)). These conflict.
- Version history: MDN's browser-compat-data lists Safari iOS **14.5** for `requestPermission`, and desktop Safari as unsupported ([mdn/browser-compat-data DeviceMotionEvent.json](https://github.com/mdn/browser-compat-data/blob/main/api/DeviceMotionEvent.json)). Developer posts date the requirement to iOS 13 ([dev.to](https://dev.to/li/how-to-requestpermission-for-devicemotion-and-deviceorientation-events-in-ios-13-46g2), via search). Since iOS 12.2 the data was off by default behind a Safari setting (same post). These conflict on the version.
- A WebKit bug notes that `requestPermission()` is exposed only in MobileSafari, not in WKWebView, where sites can read motion data without asking — [WebKit bug 203287](https://bugs.webkit.org/show_bug.cgi?id=203287) (via search summary)

**Secure context, HTTPS and self-signed certificates**
- Chromium lists "Device motion / orientation" among the powerful features already restricted to secure origins. For testing: "You can use chrome://flags/#unsafely-treat-insecure-origin-as-secure", or the `--unsafely-treat-insecure-origin-as-secure` command-line flag. "on Android and ChromeOS the command-line flag requires having a device with root access/dev mode." "On a local network, you can test on your Android device using port forwarding to access a remote host as localhost." — [Chromium: Deprecating Powerful Features on Insecure Origins](https://www.chromium.org/Home/chromium-security/deprecating-powerful-features-on-insecure-origins/)
- W3C Secure Contexts (Editor's Draft, 10 Nov 2023): "If origin's scheme is either "https" or "wss", return "Potentially Trustworthy"". Loopback 127.0.0.0/8 and ::1/128 are also potentially trustworthy. The algorithm has no certificate-validity step — [W3C Secure Contexts](https://w3c.github.io/webappsec-secure-contexts/)
- WebKit computes `isSecureContext` from the document's security origin (`isPotentiallyTrustworthy`), which is based on scheme and host (a secure scheme, or a localhost/loopback host). Certificate state is not part of the check — (source code, read 2026-11-07) [Document.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/Document.cpp), [SecurityOrigin.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/SecurityOrigin.cpp)
- Cockpit's documentation (page footer © 2013–2026, undated) says Safari's default WebSocket framework on iOS, iPadOS and ARM Macs "does not support the WebSocket Secure sessions" when the certificate is self-signed or invalid, "even when they are manually marked as trusted". Its workarounds are a valid certificate, or enabling "Apple's future/experimental WebSocket framework" (Settings > Safari > Advanced > Experimental Features) — [Cockpit: Safari](https://cockpit-project.org/running/safari)
- Current WebKit (main branch, 2026) implements WebSockets on Apple platforms with `NSURLSessionWebSocketTask`. No NSURLSession-WebSocket experimental toggle appears in UnifiedWebPreferences.yaml any more. TLS server-trust challenges for WebSocket tasks go to the authentication manager with the page's ID, the same path page loads use — (source code, read 2026-11-07) [WebSocketTaskCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/cocoa/WebSocketTaskCocoa.mm), [NetworkSessionCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/cocoa/NetworkSessionCocoa.mm), [UnifiedWebPreferences.yaml](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml)
- Community reports (via search, not first-hand): a Turris (foris-js) report says iOS still closed `wss://` with OSStatus -9807 ("invalid certificate chain") even after the self-signed certificate was installed as a trusted profile, while plain `ws://` worked. Another report describes `wss://` to a LAN IP failing on an iOS 26 beta with "The certificate for this server is invalid" — [foris-js MR 154](https://gitlab.nic.cz/turris/reforis/foris-js/-/merge_requests/154)
- mkcert: to make its certificates trusted on iOS, install `rootCA.pem` (the folder printed by `mkcert -CAROOT`), install the profile under Settings > Profile Downloaded, then "enable full trust in it". On Android, apps need user roots enabled in a development build. Latest mkcert release is v1.4.4 (2022-04-26) — [mkcert README](https://github.com/FiloSottile/mkcert)

**Generic Sensor API**
- MDN browser-compat-data: `Gyroscope` and `AbsoluteOrientationSensor` are supported in Chrome 67+, with Chrome Android and Samsung Internet mirroring Chrome. Safari (desktop and iOS) and Firefox: not supported — [mdn/browser-compat-data Gyroscope.json](https://github.com/mdn/browser-compat-data/blob/main/api/Gyroscope.json), [AbsoluteOrientationSensor.json](https://github.com/mdn/browser-compat-data/blob/main/api/AbsoluteOrientationSensor.json)
- MDN Gyroscope (last modified 13 Mar 2025): the user must grant the `'gyroscope'` permission, the API can be blocked by Permissions Policy, it is secure-context only and "not Baseline". Example: `new Gyroscope({ frequency: 60 })`. The page gives no units — [MDN Gyroscope](https://developer.mozilla.org/en-US/docs/Web/API/Gyroscope)
- Permission or Permissions-Policy names: AbsoluteOrientationSensor needs 'accelerometer', 'gyroscope' and 'magnetometer'; RelativeOrientationSensor needs 'accelerometer' and 'gyroscope'; Accelerometer, GravitySensor and LinearAccelerationSensor need 'accelerometer'; Gyroscope needs 'gyroscope'; Magnetometer needs 'magnetometer'. On frequency: "The option is a number that specifies the number of readings per second … The actual reading frequency depends on device hardware and consequently may be less than requested." Secure-context only; it can be blocked by `Permissions-Policy`. Page last modified 3 Sep 2026 — [MDN Sensor APIs](https://developer.mozilla.org/en-US/docs/Web/API/Sensor_APIs)
- Chromium caps Generic Sensor frequency at `kMaxAllowedFrequency = 60.0` Hz by default (10 Hz for magnetometer and ambient light) — (source code, read 2026-11-07) [sensor_traits.h](https://github.com/chromium/chromium/blob/main/services/device/public/cpp/generic_sensor/sensor_traits.h)

### Inferences
- **Rates.** Expect about 60 Hz from `devicemotion` on both iOS Safari and Android Chrome, based on the source constants. The Generic Sensor API in Chrome does not beat this; it is also capped at 60 Hz. For 100–200 Hz you need a native app or a no-code app.
- **Do not trust `event.interval` across platforms.** Chrome reports 16 (ms). Current WebKit code appears to report about 0.0167 (the 1/60 value in seconds). Timestamp samples with `event.timeStamp` or `performance.now()` instead. This is inferred from source and not tested on a device.
- **Sign conventions.** iOS still appears to report the opposite sign to Android and the spec for `accelerationIncludingGravity`. The 2014 report found this, and WebKit still passes CoreMotion values without negating them; CoreMotion's gravity vector points down (z ≈ -1 g when flat, face up). That CoreMotion convention is general knowledge, not verified in this session. Calibrate on each device, for example by checking the sign of z while the phone lies flat, rather than sniffing the user agent.
- **iPhone browsers.** Every iPhone browser (Chrome, Edge and Firefox for iOS) uses WebKit, so the iOS rules should apply to all of them: tap-to-request, 60 Hz, and the seconds-valued interval. This rests on App Store guideline 2.5.6, which was not fetched this session; the EU's alternative-engine option is not considered here.
- **Permission state lifetime.** WebKit keeps decisions in an in-memory per-origin map. A denial therefore probably lasts until Safari's process restarts (force-quit) or the site's website data is cleared, and the page cannot re-prompt by itself. Use a fresh origin for retests. A new trycloudflare hostname gives you one automatically.
- **Robust page pattern.** Call both `DeviceMotionEvent.requestPermission()` and `DeviceOrientationEvent.requestPermission()` directly inside a button's click or touchend handler, after feature-detecting with `typeof DeviceMotionEvent.requestPermission === 'function'`. On Chrome (M151/152 and later) this now also exists but resolves "granted", so the same code path works on both.
- **Self-signed certificates.** An HTTPS page with a self-signed certificate that the user clicked through should still be a secure context in Safari and Chrome, because secure-context status depends on scheme, not certificate validity; devicemotion should therefore work. A `wss://` connection to the same self-signed host is the fragile part on iOS: Cockpit says it fails, while current WebKit code suggests the same trust path as page loads. Untested. The reliable options are a publicly trusted certificate (a Cloudflare, ngrok or localhost.run tunnel) or an mkcert root CA installed on the iPhone with full trust enabled.
- **Android LAN testing without HTTPS.** Two shortcuts make `http://` from the laptop work on Android without certificates. One is USB port forwarding: the page is then `http://localhost:PORT`, which is a secure context. The other is chrome://flags/#unsafely-treat-insecure-origin-as-secure with the laptop's `http://IP:port` added. iOS has neither.

### Gaps
- No first-hand 2025–2026 test confirms whether iOS 26/27 Safari accepts `wss://` to a self-signed certificate after the user has accepted the HTTPS warning for the same host. The evidence conflicts (Cockpit's undated docs and community reports against the current WebKit code path).
- How long Safari remembers a motion denial, and how a user resets it (clearing website data versus restarting Safari), is not documented by Apple. The answer above is inferred from WebKit source and forum reports.
- Whether Chrome has flipped the motion-sensor default to "Ask" in any 2026 release: the Intent says "eventually"; no flip was found.
- Whether Chrome treats an HTTPS page with a bypassed certificate error as a secure context: inferred from the spec and scheme-based logic; Chromium source was not read.
- The real delivered rate of `devicemotion` on specific phones (for example, whether 120 Hz ProMotion iPhones still get 60 Hz) was not measured; the figures above come from source constants.
- MDN BCD's Safari iOS 14.5 versus the iOS 13 reports for when `requestPermission` arrived was not resolved.

## Native route: iOS CoreMotion and Android SensorManager (and what needs a Mac)

### Takeaway
On iOS, CoreMotion's `CMMotionManager` gives raw gyroscope (rad/s) and accelerometer (g) data, or fused `deviceMotion` data (bias-corrected rotation rate, gravity, user acceleration, attitude). Updates are "usually at least 100 Hz", depending on hardware. Building your own iOS app needs Xcode on a Mac. A free Apple account allows only 7-day sideloads to at most 3 devices; TestFlight and distribution need the $99/yr program. From Windows, the iOS-friendly native options are Expo Go plus expo-sensors (no Mac, no paid account) or a no-code app. On Android, `SensorManager` gives `TYPE_GYROSCOPE` (rad/s) and `TYPE_ACCELEROMETER` (m/s², including gravity). `SENSOR_DELAY_FASTEST` is 0 µs, but apps targeting Android 12 (API 31) or later are capped at 200 Hz unless they declare `HIGH_SAMPLING_RATE_SENSORS`. Android development works fully on Windows (Android Studio runs on Windows; general knowledge, not fetched this session). New and time-sensitive: Xcode 27.2 beta adds `CMMotionManager.authorizationStatus` for iOS 27.2, which suggests a coming user permission for raw motion data.

### Cited Findings

**iOS CoreMotion**
- `CMMotionManager` (iOS 4.0+, watchOS 2.0+) provides accelerometer, gyroscope, magnetometer and device-motion (sensor-fused) data. "Create only one CMMotionManager object for your app. Multiple instances of this class can affect the rate at which the system receives data from the accelerometer and gyroscope." — [Apple: CMMotionManager](https://developer.apple.com/documentation/coremotion/cmmotionmanager)
- Accelerometer: values are "measured in increments of the gravitational acceleration, with the value 1.0 representing an acceleration of 9.8 meters per second (per second)". "The maximum frequency at which you can request updates is hardware-dependent but is usually at least 100 Hz. If you request a frequency that is greater than what the hardware supports, Core Motion uses the supported maximum instead." Data is pulled via `startAccelerometerUpdates()` plus the `accelerometerData` property, or pushed via a handler — [Apple: Getting raw accelerometer events](https://developer.apple.com/documentation/coremotion/getting-raw-accelerometer-events)
- Gyroscope: "Rotation values are measured in radians per second". The same "usually at least 100 Hz" maximum applies. "The raw rotation rate data delivered by the gyroscope interfaces may be biased by other factors such as temperature. If your app requires unbiased rotation values, use the device-motion interfaces instead." Check `isGyroAvailable` first — [Apple: Getting raw gyroscope events](https://developer.apple.com/documentation/coremotion/getting-raw-gyroscope-events)
- Device motion (`deviceMotionUpdateInterval`): provides attitude, unbiased rotation rate, gravity vector, user acceleration (without gravity) and the magnetic field vector. "The maximum update frequency is hardware dependent, but is usually at least 100 Hz." The service is available from CMMotionManager, CMHeadphoneMotionManager and CMBatchedSensorManager — [Apple: Getting processed device-motion data](https://developer.apple.com/documentation/coremotion/getting-processed-device-motion-data)
- `CMDeviceMotion.rotationRate` is "gyroscope data whose bias has been removed by Core Motion algorithms"; the identically named property of CMGyroData "gives the raw data from the gyroscope" — [Apple: CMDeviceMotion.rotationRate](https://developer.apple.com/documentation/coremotion/cmdevicemotion/rotationrate)
- `gyroUpdateInterval` is in seconds and "capped to minimum and maximum values; the maximum value is determined by the maximum frequency supported by the hardware". Check the timestamps of the delivered data to learn the true interval — [Apple: gyroUpdateInterval](https://developer.apple.com/documentation/coremotion/cmmotionmanager/gyroupdateinterval)
- `CMAcceleration` uses G units: "A G is a unit of gravitation force equal to that exerted by the earth's gravitational field (9.81 m s−2)" — [Apple: CMAcceleration](https://developer.apple.com/documentation/coremotion/cmacceleration)
- **New in 2026 (beta):** Apple's docs list a type property `CMMotionManager.authorizationStatus` (returns `CMAuthorizationStatus`), introduced in iOS, iPadOS, Mac Catalyst, visionOS and watchOS 27.2 — [Apple: CMMotionManager.authorizationStatus](https://developer.apple.com/documentation/coremotion/cmmotionmanager/authorizationstatus) (JSON metadata fetched 2026-11-07). The Xcode 27.2 beta 3 header diff (header dated 2026-10-07) adds `#import <CoreMotion/CMAuthorization.h>` and the comment "Returns the current authorization status for access to motion sensor data", with `API_AVAILABLE(ios(27.2), watchos(27.2), visionos(27.2)) API_UNAVAILABLE(macos, tvos)` — [dotnet/macios wiki: CoreMotion xcode27.2 b3 (edited 2026-10-17)](https://github.com/dotnet/macios/wiki/CoreMotion-macOS-xcode27.2-b3)
- Apple's `CMBatchedSensorManager` is listed for watchOS 10+. Its documentation metadata showed odd platform data (iOS "4.0"), so iPhone support was not established — [Apple: CMBatchedSensorManager](https://developer.apple.com/documentation/coremotion/cmbatchedsensormanager)

**Windows-friendly cross-platform option: Expo / React Native**
- `expo-sensors` Gyroscope (SDK 58 reference, ~58.0.4): platforms are Android, iOS (device only) and Web; "Included in Expo Go". Values are "measured in radians per second (rad/s)", with x, y, z and `timestamp` (seconds). `setUpdateInterval(intervalMs)`; the docs' example uses 16 ms for fast. "Starting from Android 12 (API level 31), the system has a 200Hz limit for each sensor updates", and exceeding it needs `android.permission.HIGH_SAMPLING_RATE_SENSORS` in app.json — [Expo docs: Gyroscope](https://docs.expo.dev/versions/latest/sdk/gyroscope/)
- `expo-sensors` DeviceMotion (Reference v58.0.0): platforms are "Android, iOS, Web, Included in Expo Go". acceleration and accelerationIncludingGravity are in m/s², rotationRate is "Expressed in degrees per second (deg/s)", `interval` is in ms, and `orientation` is 0/90/180/-90. The config plugin's `motionPermission` sets the `NSMotionUsageDescription` text; the default is "Allow $(PRODUCT_NAME) to access your device motion". Android has the same 200 Hz note. On mobile web, call `requestPermissionsAsync()` from a user gesture, and some devices won't fire events without HTTPS — [Expo docs: DeviceMotion](https://docs.expo.dev/versions/latest/sdk/devicemotion/)
- Expo CLI (docs modified 2 Nov 2026): projects are served over LAN by default. `npx expo start --tunnel` uses ngrok (`npm i -g @expo/ngrok`); "Tunneling is slower than local connections". "Restrictive network conditions (common for public Wi-Fi), firewalls (common for Windows users) … can make it difficult to connect a remote device to your dev server over lan/localhost." "Some Windows users have also reported needing to modify their antivirus settings to allow Ngrok to work correctly." — [Expo CLI docs](https://docs.expo.dev/more/expo-cli/)

**Android SensorManager**
- Sensor types and units: `TYPE_ACCELEROMETER` is "acceleration force in m/s² … including the force of gravity". `TYPE_GYROSCOPE` is "rate of rotation in rad/s around each of the three physical axes". `TYPE_LINEAR_ACCELERATION` excludes gravity. `TYPE_GRAVITY` and `TYPE_ROTATION_VECTOR` are software or hardware sensors. `TYPE_ORIENTATION` is deprecated — [Android: Sensors overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview)
- Delays: the default `SENSOR_DELAY_NORMAL` is 200,000 µs; `SENSOR_DELAY_GAME` 20,000 µs; `SENSOR_DELAY_UI` 60,000 µs; `SENSOR_DELAY_FASTEST` 0 µs. Since API 11 you can pass microseconds directly. "The delay that you specify is only a suggested delay." "There is no public method for determining the rate … you can use the timestamps" — same source
- Rate limiting: "if your app targets Android 12 (API level 31) or higher, the system places a limit on the refresh rate" of the accelerometer, gyroscope and geomagnetic sensor. With `registerListener()`, "the sensor sampling rate is limited to 200 Hz"; with `SensorDirectChannel` it is `RATE_NORMAL`, "usually about 50 Hz". For higher rates, declare `<uses-permission android:name="android.permission.HIGH_SAMPLING_RATE_SENSORS"/>`, "Otherwise … a SecurityException occurs". If the user turns off the microphone toggle, motion sensors "are always rate-limited, regardless" — same source
- `Sensor.getMinDelay()` returns the minimum interval in µs, so it tells you the sensor's maximum rate. "A sensor's maximum data acquisition rate is not necessarily the rate at which the sensor framework delivers sensor data" — same source
- Axes: X points right, Y up, Z out of the screen in the device's natural orientation. The axes "are not swapped when the device's screen orientation changes" (use `remapCoordinateSystem`) — same source
- Background: "On devices running Android 9 (API level 28) or higher", continuous sensors such as accelerometers and gyroscopes "don't receive events" while the app is in the background. Use the foreground or a foreground service — same source

### Inferences
- **Fastest native setups.** For the highest reliable rate, use Android with your own app and the `HIGH_SAMPLING_RATE_SENSORS` permission (up to the hardware maximum from `getMinDelay()`), or 200 Hz without it. On iPhone, CoreMotion around 100 Hz, which needs either a Mac/Xcode or Expo Go.
- **Expo Go is the only no-Mac way to run your own code against native CoreMotion on an iPhone.** It needs no Apple account: you write JavaScript on Windows, run `npx expo start`, and open the project in Expo Go. You can then stream from React Native to the laptop over WebSocket or HTTP. Plan for Expo Go's single-SDK constraint, and use `--tunnel` if the venue Wi-Fi blocks LAN traffic. The rate Expo achieves on iOS (for example 100 Hz with `setUpdateInterval(10)`) was not verified.
- **iOS 27.2 permission.** If iOS 27.2 starts gating raw motion data behind a permission, apps (including Expo Go and no-code apps) may need `NSMotionUsageDescription` and a user prompt; plan a one-tap permission step in demos. Unconfirmed: only the beta header exists, and its behaviour is undocumented.
- **No permissions needed today.** Android needs no runtime permission for the accelerometer or gyroscope at 200 Hz or below. iOS `CMMotionManager` raw data has needed none historically. The latter is general knowledge, consistent with Apple's docs showing no authorization requirement until the 27.2 API.

### Gaps
- What `CMMotionManager.authorizationStatus` gates in iOS 27.2 (raw accelerometer/gyro? device motion?), and whether it ships in the release build with a prompt: no Apple documentation or release notes found yet.
- Whether `CMBatchedSensorManager` high-rate data works on iPhone, and at what rate: not verified (the Apple doc metadata looked unreliable).
- The real maximum CoreMotion rate on current iPhones (Apple says only "usually at least 100 Hz"): no 2025–2026 measurement found.
- Whether React Native/Expo Go on iOS can open `ws://` to a LAN IP without App Transport Security or Local Network prompts getting in the way: not verified.

## No-code apps that stream sensor data to a computer

### Takeaway
The quickest iPhone-to-laptop paths: **phyphox** (free and open source, iOS and Android; the phone runs an HTTP server you poll with `/get`, reading new samples since a time threshold), **Sensor Logger** (free; iOS and Android; the phone POSTs JSON batches to your URL, which can be an HTTPS tunnel), **ZIG SIM Pro** ($3.99, iOS; OSC or JSON over UDP/TCP at 1/10/30/60 messages per second), **GyrOSC** ($0.99, iOS; OSC over UDP at 1–120 messages per second) and **SensorLog** ($2.99, iOS; TCP/UDP server or client up to 100 Hz). For Android: **SensorServer** (free, GPL; the phone is a WebSocket server, `ws://ip:port/sensor/connect?type=android.sensor.gyroscope`, with Android timestamps in ns and values in rad/s), **SensaGram** (UDP JSON), **HyperIMU** (free; UDP/TCP CSV or JSON over TCP), and phyphox or Sensor Logger. Sensor Logger has no raw WebSocket output; it offers HTTP push and MQTT, and its MQTT can run over WebSockets.

### Cited Findings

**phyphox (RWTH Aachen; iOS and Android; GPL-3.0)**
- Repos: phyphox-android and phyphox-ios are GPL-3.0. The latest release on both is v1.2.1, published 2026-09-04; both repos were pushed 2026-11-05 — [GitHub phyphox-android](https://github.com/phyphox/phyphox-android), [phyphox-ios](https://github.com/phyphox/phyphox-ios) (via gh api)

- REST API (current docs mention 1.2.1 and a hardware check dated 2026-08-02):
  - Base URL is the phone's IP plus port, for example `http://192.168.0.42:8080/get`. "On iPhones the server runs on port 80". Ports can be changed in settings.

  - `/set` (POST JSON, since 1.2.1); `/config` (since 1.1.6; lists buffers and inputs; its export sets "are the best buffers to poll"); `/meta` and `/time` (since 1.1.8; `/time` maps experiment time to system time "accurate to a few milliseconds"); `/export?format=0` (Excel) or `2` (CSV as ZIP); `/res`. ### Inferences
- **Easiest iPhone option on Windows: phyphox.** It is free, needs no account, and the laptop polls `http://<phone-ip>/get?acc_time=<t>&accX=<t>|acc_time&accY=<t>|acc_time&accZ=<t>|acc_time` (port 80 on iPhone). Pass the last `acc_time` you received as the threshold `<t>` each time, so every poll returns only the new samples. This is a batched read, so you keep the full sensor rate even if you poll at 10–20 Hz. It needs direct reachability from laptop to phone, so use a phone hotspot when venue Wi-Fi isolates clients; a cloud tunnel does not help because the server is on the phone. The query pattern is derived from the documented threshold syntax and not tested.
- **Best option when venue Wi-Fi isolates devices: Sensor Logger.** The phone POSTs to any URL, so it can push to a free Cloudflare quick tunnel or ngrok URL that forwards to a Flask/FastAPI server on the laptop. This needs internet on both devices but no shared LAN and no inbound firewall rule. Watch the batch interval (a paid setting) and ngrok's 20,000 requests a month.
- **OSC/UDP apps (GyrOSC, ZIG SIM, HyperIMU UDP, SensaGram, SensorLog UDP)** need the phone and laptop on the same L2/L3 network: a hotspot or non-isolated Wi-Fi. They also need a Windows inbound UDP allow rule. HTTP tunnels like trycloudflare cannot carry raw UDP. On Python, receive with `python-osc` (for OSC) or a plain UDP socket.
- **iOS apps that send to the laptop (Sensor Logger, GyrOSC, ZIG SIM, SensorLog in client mode)** will trigger iOS's Local Network permission prompt; see the Networking section, TN3179. If it is denied, the stream silently fails until the user re-enables it in Settings > Privacy & Security > Local Network.

- Whether the free "old" ZIG SIM is still downloadable on Google Play in late 2026: not checked.
- Sensor Logger's default HTTP batch period, and whether the free tier can change it: unclear. Batch period is listed as a paid "advanced" setting.

## Networking at hackathon venues: client isolation, phone hotspots, HTTPS tunnels and mixed content

### Takeaway
Assume venue or campus Wi-Fi blocks device-to-device traffic. There are three robust patterns. (1) Put the laptop on the phone's hotspot; an iPhone hotspot needs cellular data. (2) For Android, use USB: Chrome port forwarding, or `adb forward`/`reverse` for apps like SensorServer. (3) Go through the internet with an HTTPS tunnel on the laptop: a cloudflared quick tunnel (no account; WebSockets work, SSE does not, 200 in-flight requests), ngrok (account and authtoken; free plan 20k HTTP requests a month and an HTML interstitial), or localhost.run (`ssh -R`, no account). For a mobile web page, serve the page and its WebSocket from the same HTTPS tunnel origin (`wss://same-host/ws`). An HTTPS page opening `ws://192.168.x.x` is blocked as mixed content in Safari. Chrome allows it to private IP literals only after a Local Network Access permission prompt, from M147 for WebSockets.

### Cited Findings

**Client isolation and hotspots**
- "Many more professional WIFI setups do not allow for devices to communicate to each other." Some also put devices on different subnets. The hotspot is "the most secure alternative", and Apple does not allow the iPhone hotspot without a data connection — [phyphox: Remote control](https://phyphox.org/remote-control/)
- If "Tap to Test Pushing" fails, check that both devices are on the same Wi-Fi: "Some WiFi networks, particularly corporate or university ones, may block cross-device connections". Fix: ngrok — [Sensor Logger PUSHING.md](https://github.com/tszheichoi/awesome-sensor-logger/blob/main/PUSHING.md)
- SensorServer offers a hotspot mode and USB via `adb forward` — [SensorServer README](https://github.com/umer0586/SensorServer)
- Chrome USB port forwarding: in remote debugging, enable "Discover USB devices", then "Port forwarding"; `localhost:8080` is set up by default. Open Chrome on the phone at that `localhost` port. Traffic goes over USB, so "the connection doesn't depend on your network configuration" — [Chrome DevTools: Access local servers](https://developer.chrome.com/docs/devtools/remote-debugging/local-server)
- Expo: public Wi-Fi and Windows firewalls commonly break LAN dev connections; `--tunnel` is the fallback — [Expo CLI docs (modified 2026-11-02)](https://docs.expo.dev/more/expo-cli/)

**HTTPS tunnels (all give the phone a publicly trusted HTTPS URL)**
- Cloudflare Quick Tunnels: `cloudflared tunnel --url http://localhost:8080`; "You do not need a Cloudflare account or domain"; a temporary `trycloudflare.com` hostname that changes on every run. Limits: "no uptime guarantee", "up to 200 in-flight requests" (beyond that, 429), "do not support Server-Sent Events (SSE)". The page says nothing about WebSockets — [Cloudflare Quick Tunnels (updated 2026-09-30)](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
- Cloudflare Tunnel FAQ: "Does Cloudflare Tunnel support Websockets? Yes. Cloudflare Tunnel has full support for Websockets." — [Cloudflare Tunnel FAQ (updated 2026-09-16)](https://developers.cloudflare.com/cloudflare-one/faq/tunnel/). Cloudflare closes idle WebSockets after a period with no data and may restart servers, so send ping/pong keepalives — [Cloudflare: WebSockets](https://developers.cloudflare.com/network/websockets) (via search summary)
- ngrok free plan:
  - 1 GB a month data transfer out; 20,000 HTTP requests a month (4,000 a minute); 5,000 TCP connections a month; up to 3 online endpoints; 3 agents.
  - One dev domain `your-assigned-name.ngrok-free.app` that "doesn't change when you restart the agent".
  - An interstitial page "in front of all HTML browser traffic on the free tier". Clicking through sets a 7-day cookie; send an `ngrok-skip-browser-warning` header or a non-standard User-Agent to skip it. API clients are not affected.
  - Source: [ngrok free plan limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)
- ngrok HTTP endpoints support WebSockets "without any special configuration". The ngrok WebSocket guide lists an ngrok account and authtoken as prerequisites (`ngrok http 8000`, clients use `wss://`) — [ngrok: WebSockets](https://ngrok.com/docs/using-ngrok-with/websockets) (search summary)
- localhost.run: "no account is needed for free domains"; run `ssh -R 80:localhost:8080 localhost.run`; prints a URL like `https://<id>.lhr.life` "tunneled with tls termination"; "SSH is already on macOS, Windows and Linux"; custom domains give "a stable domain and faster speeds" — [localhost.run docs](https://localhost.run/docs/), [localhost.run](https://localhost.run/)

**Mixed content and Chrome Local Network Access (LNA)**
- WebKit's `WebSocket::connect` runs `MixedContentChecker::shouldBlockRequest(frame, url)` and fails the connection asynchronously (an error event, no exception) when it is blocked. Connect-src CSP violations throw SecurityError — (source code, read 2026-11-07) [WebKit WebSocket.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/websockets/WebSocket.cpp)
- MDN: "content accessed from loopback addresses such as `http://127.0.0.1/` or `http://localhost/`" is considered secure, like HTTPS. "Mixed content requests that would otherwise be upgraded are blocked if the URL's host is an IP address rather than a domain name." Browsers auto-upgrade image, video and audio and "block insecure requests for all other resource types". The page does not mention WebSockets (last modified 15 Aug 2026) — [MDN Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content). MDN's WebSocket() constructor page (modified 22 Jun 2026) does not document mixed-content behaviour either — [MDN WebSocket()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)
- Chrome LNA (chromestatus 5152728072060928): "Chrome 142 restricted the ability to make requests to the user's local network, gated behind a permission prompt". It covers requests from a public site to local or loopback IPs, or from a local site to loopback. "This permission is restricted to secure contexts. If granted, the permissions additionally relax mixed content blocking for local network requests". Chrome 145 split the permission into `local-network` and `loopback-network` — [chromestatus: Local network access restrictions](https://chromestatus.com/feature/5152728072060928), [LNA split permissions](https://chromestatus.com/feature/5068298146414592)
- Chrome M142 stable was 2025-10-28 — [chromiumdash](https://chromiumdash.appspot.com/fetch_milestone_schedule?mstone=142)
- "WebSockets connections to local address will now start triggering permission prompts". This shipped in M147 on desktop and Android; M147 stable was 2026-04-07 — [chromestatus: LNA for WebSockets](https://chromestatus.com/feature/5197681148428288)
- M154: a `targetAddressSpace` option for the WebSocket constructor, an "escape hatch to bypass mixed content restrictions for connecting to local servers that cannot yet support HTTPS". Example: `new WebSocket("ws://local-server.example", { targetAddressSpace: "local"})`. It needs the local-network permission, and the hostname must resolve to a local IP — [chromestatus 4779920606756864](https://chromestatus.com/feature/4779920606756864)
- Chrome's LNA guide (undated, no version numbers, does not mention Android):
  - "`ws://` connections initiated from an `https://` page are exempted from Mixed Content blocking" when the host is "specifically a private or loopback IP literal". `localhost` and `.local` names also qualify.
  - "If a local endpoint is addressed via a custom non-`.local` DNS hostname, connect over `wss://`."
  - "Local Network Access permissions are denied automatically in insecure (`http://`) top-level contexts."
  - Checks apply "only when a request crosses from a *less private* address space into a *more private* address space". Local means RFC 1918, link-local, IPv6 ULA and `.local`; loopback means 127.0.0.0/8, ::1/128 and localhost.
  - Source: [Chrome: Local Network Access guide](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access)

**iOS Local Network privacy (native and no-code apps)**
- "The first time a program accesses the local network, the system displays an alert asking the user to approve that access." Users manage this in Settings > Privacy & Security > Local Network. "Making an outgoing TCP connection" requires it, and so does "Sending a UDP unicast"; "Listening for and accepting incoming TCP connections" does not. "Traffic originating from WKWebView, SFSafariViewController, and Safari doesn't require local network access." — [Apple TN3179: Understanding local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)

### Inferences
- **Recommended mobile-web architecture.** Run one laptop server (for example FastAPI or Node) that serves `index.html` and a `/ws` WebSocket endpoint on one port, and expose it with `cloudflared tunnel --url http://localhost:8000`. On the phone, open `https://<random>.trycloudflare.com`, tap "Start" to call `requestPermission()`, then stream JSON to `wss://<same-host>/ws`. This gives a secure context, needs no certificates, avoids mixed content, and works under client isolation, because both devices only need internet. The cost is extra latency through Cloudflare and dependence on venue internet. Latency was not measured; expect tens of milliseconds or more.
- **Prefer one WebSocket over many POSTs through tunnels.** ngrok free allows 20,000 HTTP requests a month, so a 10 Hz POST loop would use that up in about 33 minutes, while one WebSocket upgrade is a single request (an inference from the documented limits). Cloudflare quick tunnels' 200-in-flight limit also favours a single socket.
- **Lowest latency and no internet: a hotspot plus a LAN server.** Android Chrome can then reach `http://laptop-ip:port` only if the origin is made secure (port forwarding, the insecure-origin flag, or HTTPS). iOS Safari needs HTTPS with a trusted certificate: mkcert's root CA installed and fully trusted on the iPhone, or the tunnel approach. Self-signed `wss://` on iOS is the riskiest choice (see the web section).
- **Windows firewall.** When the laptop is the server (Sensor Logger push, UDP/OSC receivers, a LAN web server), Windows Defender Firewall must allow the inbound port for the active network profile. New networks, including a phone hotspot, are often marked "Public", which commonly blocks this. Tunnels avoid the problem because cloudflared, ngrok and ssh make outbound connections. This rests on general Windows knowledge, plus Expo's and SensaGram's notes that Windows firewalls block connections; no Microsoft doc was fetched.
- **iPhone hotspot.** The laptop joins it, typically on a 172.20.10.x subnet (community reports only, not official). The phone needs cellular data for the hotspot to turn on, per phyphox.

### Gaps
- No official statement that Cloudflare *quick* tunnels (trycloudflare) support WebSockets: the general Tunnel FAQ says yes, and the quick-tunnel page lists only SSE as unsupported. Test before the event.
- Whether localhost.run free tunnels support WebSockets, and how long free URLs last: not documented on the pages fetched.
- Whether ngrok's free plan allows TCP endpoints without a payment method (the limits page lists 5,000 TCP connections a month): not verified.
- iPhone Personal Hotspot addressing (172.20.10.x) and whether hotspot clients can always reach each other: no Apple document found.
- Real-world latency of the different routes (LAN WebSocket, hotspot, tunnel): no measurements found.
- How common client isolation is at specific venues (for example, campus eduroam networks): no data found.
