# AirPods and Apple headphone motion data for developers (as of 2026-11-07)

Status: complete (2026-11-07). Source dates are "accessed 2026-11-07" unless the page shows its own date. "Apple doc JSON" means the raw DocC JSON behind developer.apple.com, fetched 2026-11-07 (for example https://developer.apple.com/tutorials/data/documentation/coremotion/cmheadphonemotionmanager.json). GitHub READMEs and code were read with `gh api` on 2026-11-07.

## Which platforms, OS versions and headphone models support CMHeadphoneMotionManager?

### Takeaway
`CMHeadphoneMotionManager` (Core Motion) is the only public Apple API for AirPods motion. Apple lists it on iOS 14+, iPadOS 14+, Mac Catalyst 14+, macOS 14+ and watchOS (doc metadata says 7.0, but Apple's change log says AirPods motion on watchOS arrived in June 2024, which means watchOS 11). It is not offered on visionOS or tvOS. It works with headphones that support Spatial Audio with dynamic head tracking: AirPods 3, 4 and 5, every AirPods Pro, AirPods Max and Max 2, and (reported by third parties, not documented by Apple) Beats Fit Pro.

### Cited Findings

You can also use CMHeadphoneMotionManager to support AirPods device motion data on watchOS." The same entry adds `CMHeadphoneActivityManager`. The page has no later headphone entries (its newest entry is September 2024). — [Apple: Core Motion updates](https://developer.apple.com/documentation/updates/coremotion) (accessed 2026-11-07)
- Before that change, a developer reported (October 2023) that on watchOS "isDeviceMotionAvailable property is false" with AirPods Pro, while "the same code on iOS everything works fine"; no Apple reply. — [Apple Developer Forums thread 739005](https://developer.apple.com/forums/thread/739005)

### Inferences
- Practical support set for new work (late 2026): AirPods Pro 2 and 3, AirPods 4 (both versions), AirPods 5, AirPods Max (Lightning and USB-C) and Max 2. AirPods Pro 1 and AirPods 3 should also work but are older and appear less in recent tests. Gate on `isDeviceMotionAvailable` at runtime rather than on a model list.
- On a Mac, plan for Apple silicon and macOS 14+: Apple ties head tracking to Apple silicon, and the API starts at macOS 14.
- The watchOS "7.0" in Apple's doc metadata conflicts with Apple's own change log and the 2023 forum report; treat watchOS 11 as the real floor for AirPods motion on Apple Watch.
- Several Apple doc pages show inherited "iOS 14.0" availability for members (for example `startConnectionStatusUpdates()`), but Apple's change log dates connection monitoring outside a motion session to June 2024 (iOS 18 / macOS 15 / watchOS 11 cycle). Use `if #available` checks for those members.

### Gaps
- No Apple page lists which Beats models deliver data through `CMHeadphoneMotionManager`; only Beats Fit Pro has third-party confirmation. Beats Studio Pro, Solo 4, Powerbeats Pro 2, Powerbeats Fit and Beats 360 are unconfirmed.
- No source found on whether the API delivers data when AirPods Max are used over the USB-C cable.

## What does the API deliver (fields, units, rate, latency), what permissions are needed, and what is new (iOS 18 head gestures, iOS 26 and 27)?

### Takeaway
The API delivers fused `CMDeviceMotion` samples (attitude as quaternion, rotation matrix and roll/pitch/yaw in radians; bias-corrected rotation rate in rad/s; gravity and user acceleration in g; timestamp; and `sensorLocation` telling which bud sent the sample), one bud at a time. There is no raw IMU, no rate setting and no documented rate or latency: measurements range from 25 Hz (older AirPods, iPhone) to 50 Hz (AirPods Pro 2 on macOS 26, and AirPods Max 2 via the reverse-engineered route), with packet loss under ANC and at distance. The only permission is `NSMotionUsageDescription` (Motion & Fitness); missing it crashes the app. No public head-gesture (nod/shake) API was found; iOS 18 added `CMHeadphoneActivityManager` and connection-status monitoring, iOS 26 added nothing for motion, and iOS 27 adds only batched, research-only SensorKit headphone motion (`CMRecordedDeviceMotion`).

### Cited Findings
Data fields and units
- `CMDeviceMotion`: "Encapsulated measurements of the attitude, rotation rate, and acceleration of a device." Topics: `attitude`, `rotationRate`, `gravity`, `userAcceleration`, `magneticField`, `heading`, `sensorLocation`. — [Apple doc: CMDeviceMotion](https://developer.apple.com/documentation/coremotion/cmdevicemotion)
- `CMAttitude` "offers three different mathematical representations of attitude: a rotation matrix, a quaternion, and Euler angles (roll, pitch, and yaw values)"; roll, pitch and yaw are "in radians"; `multiply(byInverseOf:)` "Yields the change in attitude given a specific attitude." — [Apple doc: CMAttitude](https://developer.apple.com/documentation/coremotion/cmattitude)
- `rotationRate`: "a measurement of gyroscope data whose bias has been removed by Core Motion algorithms" (raw gyro is only in `CMGyroData`, which headphones do not provide). — [Apple doc: rotationRate](https://developer.apple.com/documentation/coremotion/cmdevicemotion/rotationrate). Third-party docs give the unit as rad/s. — [AWARE AirPods sensor](https://github.com/awareframework/com.awareframework.ios.sensor.airpods); [changtimwu/airpod-pose-estimate](https://github.com/changtimwu/airpod-pose-estimate)
- `CMAcceleration` axes are "acceleration in G's (gravitational force)"; "A G is a unit of gravitation force equal to that exerted by the earth's gravitational field (9.81 m s−2)." Total acceleration = `gravity` + `userAcceleration`. — [Apple doc: CMAcceleration](https://developer.apple.com/documentation/coremotion/cmacceleration); [Apple doc: userAcceleration](https://developer.apple.com/documentation/coremotion/cmdevicemotion/useracceleration)
- `CMDeviceMotion.SensorLocation` cases: `.default`, `.headphoneLeft` ("The sensor is in the left headphone"), `.headphoneRight`. — [Apple doc: SensorLocation](https://developer.apple.com/documentation/coremotion/cmdevicemotion/sensorlocation-swift.enum)
- WWDC23: "motion data is delivered to you from one bud at a time. The SensorLocation enum delivered with each sample lets you identify which bud sourced the data"; if the streaming bud is removed with Automatic Ear Detection on, "my left bud will take over the data stream." It recommends storing a `startingPose` and using `multiply` to get motion relative to it. — [Apple WWDC23 session 10179](https://developer.apple.com/videos/play/wwdc2023/10179)
- Apple's class page shows the headphone coordinate axes in an illustration ("the positive x-axis, positive y-axis, and positive z-axis for motion-capable Apple headphones") but gives no text description of the reference frame. — [Apple doc: CMHeadphoneMotionManager](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanager)
- Third-party SDK reading: no `deviceMotionUpdateInterval` and no reference-frame parameter exist on `CMHeadphoneMotionManager`; magnetic field and heading are not filled "in a known way" by headphones; `CMLogItem.timestamp` is seconds since boot ("Mach absolute time" in the macOS 27 header). — [Subvox research note, 2026-10-31](https://github.com/andreaspitzer/subvox/blob/research/cmheadphonemotionmanager-facts/docs/research/cmheadphonemotionmanager-facts.md) (secondary)

API surface and connection handling
- Members: `isDeviceMotionAvailable`, `isDeviceMotionActive`, `isConnectionStatusActive`, `authorizationStatus()`, `startDeviceMotionUpdates()` (pull; read `deviceMotion`, which "is nil when there is no device-motion data"), `startDeviceMotionUpdates(to:withHandler:)` (push on an `OperationQueue`), `stopDeviceMotionUpdates()`, `startConnectionStatusUpdates()`, `stopConnectionStatusUpdates()`, `delegate`. — [Apple doc: CMHeadphoneMotionManager](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanager)
- `CMHeadphoneMotionManagerDelegate`: optional `headphoneMotionManagerDidConnect(_:)` and `headphoneMotionManagerDidDisconnect(_:)`. — [Apple doc: CMHeadphoneMotionManagerDelegate](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanagerdelegate)
- WWDC23: with Automatic Ear Detection, "You'll get a disconnect event when the buds are taken out of ear, and a connect event when they're put back in"; for over-ear headphones with automatic head detection, "putting on and taking off over ear headphones will trigger these events." — [Apple WWDC23 session 10179](https://developer.apple.com/videos/play/wwdc2023/10179)
- The react-native-headphone-motion docs note that stopping updates triggers a disconnect event ("the system automatically disconnect your headphone from your app if you stopped getting motion updates"). — [XHMM/react-native-headphone-motion](https://github.com/XHMM/react-native-headphone-motion) (secondary)

Permissions
- "In iOS and macOS, include the NSMotionUsageDescription key in your app's Info.plist file. If this key is absent, the system crashes your app when you start device-motion updates." — [Apple doc: CMHeadphoneMotionManager](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanager). `CMHeadphoneActivityManager` has the same rule ("terminates your app"). — [Apple doc: CMHeadphoneActivityManager](https://developer.apple.com/documentation/coremotion/cmheadphoneactivitymanager)
- On macOS the host app itself must carry the key: SC AirPods "requires a special build of SuperCollider since macOS demands the NSMotionUsageDescription attribute"; SuperCollider 3.15-dev adds it. — [capital-G/sc_airpods](https://github.com/capital-G/sc_airpods)
- The simulator returns no headphone motion; a physical iPhone with AirPods connected to that phone is needed. — [narasim-teja/chewww](https://github.com/narasim-teja/chewww); Apple's sample also must "run on a device, not in Simulator." — [Apple sample code](https://developer.apple.com/documentation/coremotion/getting-motion-activity-data-from-headphones)

Update rate (none of these come from Apple documentation)
- Apple publishes no headphone motion rate; the 100 Hz figure in WWDC23 applies to `CMMotionManager`, not headphones. — [Apple WWDC23 session 10179](https://developer.apple.com/videos/play/wwdc2023/10179); [Subvox research note](https://github.com/andreaspitzer/subvox/blob/research/cmheadphonemotionmanager-facts/docs/research/cmheadphonemotionmanager-facts.md)
- Measured 25 Hz, AirPods Pro to iPhone: "uniformly sampled at 40 ms intervals with a 25 Hz sampling rate", but intervals "deviate significantly, by multiples of 40 ms, indicating data loss"; loss "is particularly severe during 'ANC' and 'Trans' modes"; at "15 m separation and wall obstructions, packet loss exceeds 30%". — [Fu et al., TWSCardio, arXiv 2501.06744, January 2025](https://arxiv.org/abs/2501.06744)
- Measured 25 Hz, AirPods 3: "The iPhone and Watch both sampled at 100 Hz, while the AirPods sampled at 25 Hz." — [Suite-IN, arXiv 2411.07828, November 2024](https://arxiv.org/abs/2411.07828)
- Measured 50 Hz, AirPods Pro 2 on macOS 26: "50.0 Hz, steady 20.0 ms between samples"; "25 Hz on older hardware". — [changtimwu/airpod-pose-estimate](https://github.com/changtimwu/airpod-pose-estimate) (2026-09-20)
- Measured about 50 Hz, AirPods Max 2 (firmware 8E258) on Windows through the reverse-engineered AAP channel (not the Apple API): "It streams motion at about 50 Hz". — [FIocker/aap-head-tracker](https://github.com/FIocker/aap-head-tracker) (2026-07-26)
- Claimed, not measured: "approximately 100 Hz" — [AWARE AirPods sensor](https://github.com/awareframework/com.awareframework.ios.sensor.airpods) (2026-06); "60-100 Hz (device dependent)" and "up to 100Hz" — [MakersPortal MotionLink](https://makersportal.com/apps/motionlink) (March 2026)

Latency
- Apple publishes no latency or jitter figure for headphone motion. — [Subvox issue #3, 2026-10-31](https://github.com/andreaspitzer/subvox/issues/3)
- TWSCardio reports that AirPods use a short BLE supervision timeout (about 100 ms) "to ensure low latency", and that the AirPods series is "configured with a minimal packet interval of 40ms". — [arXiv 2501.06744](https://arxiv.org/abs/2501.06744)
- airpod-pose-estimate lists "Fine timing — Bluetooth latency makes twitchy input mushy" among the limits. — [changtimwu/airpod-pose-estimate](https://github.com/changtimwu/airpod-pose-estimate)

Audio-session interaction (HFP)
- Developers report that motion updates stop when the app uses the AirPods microphone: "If I add options: .allowBluetooth, the IMU update will stop" (May 2021); it works "when either play only or record only"; reports continue to February 2024 with no Apple reply. — [Apple Developer Forums thread 681301](https://developer.apple.com/forums/thread/681301) (read 2026-11-07 by the earlier researcher)

Background
- No Apple document describes background delivery for headphone motion. A 2022 forum question reports gyro data stops when the app goes to the background; the only reply (community, not Apple) wrongly calls "Motion & Fitness" a background mode. — [Apple Developer Forums thread 715100](https://developer.apple.com/forums/thread/715100)
- A forum report says device-motion callbacks (`CMMotionManager`) stop a few seconds after the app leaves the foreground unless a Core Location session is running; with the debugger attached the app is not suspended, which hides the problem. — [Apple Developer Forums thread 841001](https://developer.apple.com/forums/thread/841001) (search summary only; not opened)

Newer APIs
- iOS 18 / macOS 15 / watchOS 11 (June 2024): `CMHeadphoneActivityManager` and connection monitoring outside a motion session. — [Apple: Core Motion updates](https://developer.apple.com/documentation/updates/coremotion)
- iOS 27 / macOS 27 (2026): new `CMRecordedDeviceMotion` class (properties `identifier`, `startDate`), listed for iOS, iPadOS, Mac Catalyst, macOS, visionOS and watchOS 27. — [Apple doc: CMRecordedDeviceMotion](https://developer.apple.com/documentation/coremotion/cmrecordeddevicemotion)
- iOS 27 SensorKit `SRSensor.headphoneMotion` (iOS, iPadOS, Mac Catalyst 27): "Sensor stream for headphone motion collection ... acceleration measured by the device's accelerometer, rotation rate measured by the device's gyroscope, altitude"; fetches return `CMRecordedDeviceMotion` arrays. SensorKit needs the `com.apple.developer.sensorkit.reader.allow` entitlement, "required by your app's preapproved research study." — [Apple doc: SRSensor.headphoneMotion](https://developer.apple.com/documentation/sensorkit/srsensor/headphonemotion); [Apple doc: SensorKit](https://developer.apple.com/documentation/sensorkit)
- iOS 26: the AirPods addition for developers is audio, not motion. `AVAudioSession.CategoryOptions.bluetoothHighQualityRecording` (iOS 26.0, iPadOS 26.0, Mac Catalyst 26.0) "enables full-bandwidth audio when the Bluetooth route supports it, such as on certain AirPods models"; "Bluetooth high-quality recording isn't currently supported in the European Union." — [Apple doc: bluetoothHighQualityRecording](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/bluetoothhighqualityrecording). A third-party SDK diff found no motion changes in the 26.x or 27.0 headphone headers. — [Subvox research note](https://github.com/andreaspitzer/subvox/blob/research/cmheadphonemotionmanager-facts/docs/research/cmheadphonemotionmanager-facts.md) (secondary)- Head gestures arrived with iOS 18 as a system feature ("Siri Interactions"): users "nod their head yes or gently shake their head no to respond to Siri announcements" and calls, on AirPods Pro 2 (H2 chip). — [iMore, June 2024](https://www.imore.com/airpods/your-airpods-pro-earbuds-are-getting-some-hot-new-tricks-including-voice-isolation-personalized-spatial-audio-in-games-and-more-in-ios-18); [Engadget](https://engadget.com/airpods-pro-update-adds-head-nodding-gesture-to-silently-respond-to-siri-174141928.html) (secondary news coverage; Apple's newsroom text was not opened)
- Third parties build their own nod/shake detectors on the motion stream: LibrePods (`GestureDetector.kt`, peak, rhythm and confidence thresholds) — [librepods-org/librepods](https://github.com/librepods-org/librepods); HeadOrbit (turn, nod and tilt mapped to actions) — [Cogria-AI/HeadOrbit](https://github.com/Cogria-AI/HeadOrbit)

### Inferences
- Design for 25 to 50 Hz with gaps, measure the real rate from `diff(timestamp)` per session, and log `sensorLocation` so bud switches can be detected. Treat yaw as relative (drifts, no compass).
- To detect nods and shakes in your own app, threshold `rotationRate` or relative pitch/yaw yourself; there is no Apple callback.
- Do not route microphone input through the AirPods while you need motion. iOS 26 high-quality Bluetooth recording might avoid the HFP switch that stops motion updates, but no source reports testing motion while it is on, so measure before relying on it.
- For background use, keep the app alive with a real background mode (audio playback or location) and test on a device without the debugger attached; this is not documented by Apple.

### Gaps
- No Apple figure exists for rate, latency or jitter. No rigorous end-to-end motion latency measurement was found. A Medium article on AirPods Spatial Audio round-trip latency (reported mean about 204 ms on iOS 14) could not be opened (HTTP 403), so it is not used as a finding.
- Whether the API timestamp is set on the AirPods or on arrival at the phone is undocumented.
- No Apple statement on background delivery or on the HFP microphone conflict.
- No public developer API for AirPods head gestures (nod/shake) was found: Apple's Core Motion pages, the Core Motion change log, forum threads and news searches (2026-11-07) mention only the consumer feature. Absence is hard to prove; a check of the iOS 27 SDK headers for "gesture" would settle it.

## Which open-source projects and apps expose or stream AirPods motion?

### Takeaway
Many small projects wrap `CMHeadphoneMotionManager`; all of them run on Apple hardware (iPhone, iPad or Mac), and most are hobby-grade with few stars. The useful ready-made outputs are OpenTrack UDP (SmoothTrack on iPhone; AirTracker and airpods-head-tracking on Mac), JSON over UDP (Kishimen on iPhone; AirTracker port 4243; airpod-pose-estimate), HTTP/MQTT push (Sensor Logger on iPhone), browser bridges (Poddle Helper on Mac; NativeWebKit.js on iOS) and framework wrappers (Unity, Flutter, React Native, SuperCollider). No App Store app that streams AirPods motion as OSC was found.

### Cited Findings
App Store apps (iPhone/iPad; no developer account needed)
- SmoothTrack (John Goering), £14.99 UK / $14.99 US: "AirPods Pro" mode "will utilize AirPods Pro 3DOF head *direction* data (note: direction, not position)"; "You can optionally combine this with the face tracking for 6DOF"; sends to OpenTrack, with "USB connection mode - lower your latency by directly connecting to your PC via USB"; requires iOS 26.0 or later; version 2.02 (13 Oct). — [App Store UK: SmoothTrack](https://apps.apple.com/gb/app/smoothtrack/id1528839485) (accessed 2026-11-07); US price from [App Store US: SmoothTrack](https://apps.apple.com/us/app/smoothtrack/id1528839485) (read 2026-11-07 by the earlier researcher)
- Sensor Logger (Logger Labs LTD), free with in-app purchases (Plus $4.99/month up to Ultimate $249.99/year): the measurement list includes "Headphone Motion (AirPods)"; "stream data via HTTP or MQTT"; requires iOS 16.4 or later; version 1.68.1. A user review says "I can not record motion data from AirPods." — [App Store US: Sensor Logger](https://apps.apple.com/us/app/sensor-logger/id1531582925) (accessed 2026-11-07)

Open-source, Mac (macOS 14+)

### Inferences
- For a Windows game or tool that already accepts OpenTrack input, SmoothTrack is the quickest no-code route: iPhone plus AirPods Pro, Wi-Fi or USB to OpenTrack on Windows, rotation only.
- For custom data on Windows, Sensor Logger (HTTP or MQTT to a Windows server) is the cheapest ready-made option, but whether its headphone channel is included in pushes must be tested.
- OSC output would need a small bridge on Windows (UDP JSON or OpenTrack packets in, OSC out).

### Gaps
- No App Store app that streams AirPods motion as OSC was found (the earlier researcher's search also found none).
- Sensor Logger's documentation does not say explicitly that headphone motion is included in HTTP/MQTT pushes, or at what rate.
- The App Store status of the NativeWebKit companion app was not checked.

## Can AirPods motion be read without the Apple API (LibrePods, Android, Linux, Windows)?

### Takeaway
Yes, experimentally. AirPods send head-tracking packets over Apple's proprietary AAP/AACP protocol on Bluetooth Classic L2CAP PSM 0x1001 once a start command is sent. LibrePods (Android, plus older Python scripts for Linux) and two Windows bridges built on the third-party MagicAAP driver decode them. The data is less complete than Apple's API (orientation only, or in LibrePods just pitch, yaw and two acceleration values), the packet format varies by model and firmware, Android often needs root plus Xposed, and Windows needs a kernel driver that may require Test Mode. Each Windows project is confirmed on only one or a few devices (aap-head-tracker: AirPods Max 2 at about 50 Hz).

### Cited Findings
- LibrePods "implements the proprietary protocol used to exchange data between AirPods and Apple devices, enabling features like changing noise control modes, fast ear detection, accurate battery status, head gestures, conversational awareness, and more on non-Apple platforms." Feature table: Head Gestures — Linux ⛔, Android ✅; Head-tracked Spatial Audio — ❓ on both. "The app does not currently provide head tracking information to Android for the OS to perform HRTF. This has not been explored completely, and it might need root." 30,658 stars; GPL-3.0; last push 2026-10-28. — [librepods-org/librepods README](https://github.com/librepods-org/librepods)
- LibrePods Android root rule: features needing the VendorID hook "will always require root"; on "ColorOS/OxygenOS 16 and realme UI 7.0 and Pixel devices on Android 16 QPR3 (with the latest Google Play system update), LibrePods does not need root for most features"; elsewhere it "needs root because of a bug in the Android Bluetooth stack Fluoride" and "You must have Xposed installed"; the bug "has already been resolved and should be available in Android 17 for all devices"; it is on Google Play for supported combinations. — [LibrePods Android README](https://github.com/librepods-org/librepods/blob/main/android/README.md)
- LibrePods code: AACP opcode `HEADTRACKING = 0x17` with start and stop packets (`sendStartHeadTracking()`) and header bytes `04 00 04 00`. — [AACPManager.kt](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/bluetooth/AACPManager.kt). The parser reads three 16-bit orientation values (bytes 43-48) and two acceleration values (bytes 51-54), calibrates on 10 samples, and outputs only `Orientation(pitch, yaw)` and `Acceleration(vertical, horizontal)`. — [HeadOrientation.kt](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/utils/HeadOrientation.kt). `GestureDetector.kt` detects nods and shakes from this stream with peak, rhythm and confidence thresholds. — [GestureDetector.kt](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/utils/GestureDetector.kt)
- LibrePods Linux Python visualiser (branch `linux/rust`, folder `head-tracking/`, added 2025-03-14 in "android+linux: add head tracking and gestures"): connects with PyBluez `BluetoothSocket(bluetooth.L2CAP)` to PSM `0x1001` and sends START `04 00 04 00 17 00 00 00 10 00 10 00 08 A1 02 42 0B 08 0E 10 02 1A 05 01 40 9C 00 00`; computes `pitch = (o2_norm + o3_norm) / 2 / 32000 * 180` and `yaw = (o2_norm - o3_norm) / 2 / 32000 * 180` ("assuming a sensor range around 32000"); `gestures.py` detects "Yes" and "No". — [LibrePods head-tracking README](https://github.com/librepods-org/librepods/blob/linux/rust/head-tracking/README.md); [connection_manager.py](https://github.com/librepods-org/librepods/blob/linux/rust/head-tracking/connection_manager.py)
- O-Pose (Android, Chinese README): for OPPO/ColorOS 16 (Android 16), reads AirPods Pro 2 AACP head tracking directly and decodes a quaternion into pitch and yaw, then bridges over TCP `127.0.0.1:53987` to drive system spatial audio; uses a "constant 20 ms high-speed mode" judged stable "above 40 Hz"; tested on a OnePlus 13T with APatch root + Zygisk + LSPosed + Shizuku. — [fengkaobanli/O-Pose](https://github.com/fengkaobanli/O-Pose) (last push 2026-09-28; quotes translated)
- Windows, aap-head-tracker (C#, .NET 9): "uses the third-party MagicAAP kernel driver to reach Apple's Bluetooth Classic AAP channel, starts the devmotion6 sensor service, decodes the fused orientation quaternion, and sends an OpenTrack-compatible UDP pose." Confirmed only on AirPods Max 2 (A3454, firmware 8E258) at "about 50 Hz"; AirPods 3 and 4, AirPods Pro 1-3, AirPods Max 1 and Beats are untested candidates; "Firmware may assign a different RTBuddy service ID or use a different report layout"; Windows 11 tested; the driver "may require administrator access, Windows Test Mode, or a compatible signed build"; "Only one application should consume the MagicAAP stream at a time"; developed "with the paired iPhone's Bluetooth disabled". — [FIocker/aap-head-tracker](https://github.com/FIocker/aap-head-tracker) (created 2026-07-26)
- Windows, airpods-head-track (Rust): AirPods "broadcast head tracking data over Bluetooth L2CAP using Apple's proprietary AACP ... on PSM 0x1001. The Windows Bluetooth stack does not expose L2CAP sockets to userspace, so this tool relies on the MagicAAP kernel driver"; it sends yaw, pitch and roll to OpenTrack on `127.0.0.1:4242`; MagicAAP "requires Windows Test Mode to be enabled because it is not digitally signed" (`bcdedit /set testsigning on`); it fails if MagicPods holds the device. — [StarNumber12046/airpods-head-track](https://github.com/StarNumber12046/airpods-head-track) (last push 2026-07-28)
- MagicAAP page: driver to "Unlock additional features for AirPods (all models) and Beats"; "Official (unsigned) — requires Windows to be in Test Mode"; "Community (signed by a member of our community)" that "Works on Windows versions prior to the April 2026 update"; no mention of head tracking, price or licence. — [MagicPods: MagicAAP](https://magicpods.app/magicaap/) (accessed 2026-11-07)

### Inferences
- Reverse-engineered routes give orientation (and rough acceleration), not Apple's full `CMDeviceMotion` (no documented units, no bias-corrected gyro, no gravity split). Treat them as research tools, not a dependable product base.
- On a fully updated Windows 11 PC, the signed community MagicAAP build may not load (it is stated to work only before the April 2026 update), which leaves Test Mode with the unsigned driver. Test Mode lowers system security, and some anti-cheat software refuses to run with it.
- Android is the most mature non-Apple route (LibrePods is on Google Play for some phones, and nod/shake gestures work), but LibrePods does not expose a stream to other apps; you would change its GPL-3.0 code to forward packets.

### Gaps
- No source gives the AACP head-tracking packet rate for LibrePods, or which AirPods models and firmware versions it covers.
- MagicPods/MagicAAP price and licence were not found on the page.
- Whether Apple firmware updates break these start packets is undocumented; aap-head-tracker already needs several start formats.

## What is the most practical route for a Windows 11 developer without a Mac?

### Takeaway
A Mac is not required. The official API still needs an iPhone, iPad or Mac to talk to the AirPods, so the practical pattern is "Apple device reads `CMHeadphoneMotionManager`, sends UDP/HTTP to the Windows PC". In order of effort: (1) buy SmoothTrack (about $14.99, iOS 26+) and receive OpenTrack UDP on Windows (rotation only, "AirPods Pro" mode); (2) use the free Sensor Logger app's HTTP/MQTT push to a small Windows server (headphone inclusion must be tested); (3) if you have an iPad, write your own app in the free Swift Playgrounds app (it supports the `.motion` capability), with no Mac and no paid account; (4) for a custom iPhone app, build on Windows with xtool (WSL) or in a cloud macOS runner and sideload with a free Apple Account (re-sign every 7 days, 3 apps), or pay $99/year for the Apple Developer Program, which Expo EAS internal distribution requires. A Windows-only route with no Apple device exists (MagicAAP driver plus aap-head-tracker or airpods-head-track to OpenTrack), but it is experimental, may need Windows Test Mode, and is confirmed on very few AirPods models.

### Cited Findings
What needs what (Apple accounts)
- Apple Developer Program: "The Apple Developer Program is 99 USD per membership year"; fee waivers exist for eligible nonprofits, accredited educational institutions and government entities. — [Apple: Enroll](https://developer.apple.com/programs/enroll/) (accessed 2026-11-07)
- Free Apple Account ("Personal Team") limits: "You can register up to 10 App IDs, which expire after 7 days." "You can register up to 3 devices, which expire after 7 days." "You can install up to 3 apps per device. Provisioning profiles that enable apps to be installed on a device will expire 7 days from issuance. You'll need to rebuild and reinstall your app to your device after expiration." — [Apple: Choosing a Membership](https://developer.apple.com/support/compare-memberships/) (accessed 2026-11-07)
- Expo EAS internal distribution (ad hoc): "This method requires a paid Apple Developer account"; ad hoc is limited to 100 iPhones per year; devices are registered with `eas device:create`. — [Expo docs: Internal distribution](https://docs.expo.dev/build/internal-distribution/) (modified 2026-11-02). EAS store builds also need the paid membership. — [Expo docs: Build setup](https://docs.expo.dev/build/setup/) (read 2026-11-07 by the earlier researcher)
- The only React Native wrapper is a native module installed with `npm install react-native-headphone-motion` and `npx pod-install`, and the app must declare `NSMotionUsageDescription`. — [XHMM/react-native-headphone-motion](https://github.com/XHMM/react-native-headphone-motion)

Route: existing App Store apps (no code, no developer account)
- SmoothTrack sends AirPods Pro "3DOF head direction data" to OpenTrack over the network or "USB connection mode"; £14.99 UK / $14.99 US; iOS 26.0+. — [App Store UK: SmoothTrack](https://apps.apple.com/gb/app/smoothtrack/id1528839485)
- OpenTrack's "UDP over network" input listens on port 4242; projects send "6 doubles" (x, y, z, yaw, pitch, roll). — [StarNumber12046/airpods-head-track](https://github.com/StarNumber12046/airpods-head-track); [crippler95/airtracker](https://github.com/crippler95/airtracker)
- Sensor Logger is free (paid tiers optional), lists "Headphone Motion (AirPods)", and can "stream data via HTTP or MQTT"; pushes are JSON POSTs, and the docs show a Python server and "Tap to Test Pushing". — [App Store: Sensor Logger](https://apps.apple.com/us/app/sensor-logger/id1531582925); [PUSHING.md](https://github.com/tszheichoi/awesome-sensor-logger/blob/main/PUSHING.md)

Route: Swift Playgrounds on an iPad (free)
- Swift Playgrounds is "a revolutionary app for iPad and Mac" (iPhone is not listed); it is free; "on iPad your playgrounds respond to touch gestures and interact with hardware, such as the accelerometer, gyroscope, and camera"; you can "submit your app to App Store Connect". — [Apple: Swift Playgrounds](https://developer.apple.com/swift-playgrounds/) (accessed 2026-11-07)
- A working Swift Playgrounds headphone-motion app exists; its generated manifest uses `capabilities: [.motion(purposeString: "Headphone Motion Tracking")]` (this supplies the motion usage string) and needs Swift Playgrounds 4.3+ on iPadOS 16.1+. — [kkebo/HeadphoneMotionTracking.swiftpm](https://github.com/kkebo/HeadphoneMotionTracking.swiftpm)

Route: build an iPhone app without a Mac
- xtool: "Cross-platform Xcode replacement. Build and deploy iOS apps with SwiftPM on Linux, Windows, macOS" (14,909 stars; release 1.24.0 on 2026-10-26). - Cloud macOS build machines: "Standard GitHub-hosted runners in public repositories" are free; otherwise "macOS 3-core or 4-core (M1 or Intel)" costs $0.062 per minute, and GitHub Free includes $12 of compute per month. — [GitHub Docs: GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) (accessed 2026-11-07; the page does not say explicitly that macOS counts as "standard")

Route: Windows only, no Apple device
- MagicAAP driver plus [FIocker/aap-head-tracker](https://github.com/FIocker/aap-head-tracker) (C#, OpenTrack UDP, AirPods Max 2 confirmed at about 50 Hz) or [StarNumber12046/airpods-head-track](https://github.com/StarNumber12046/airpods-head-track) (Rust, OpenTrack UDP). The official MagicAAP driver is unsigned and "requires Windows to be in Test Mode"; the community-signed build "Works on Windows versions prior to the April 2026 update". — [MagicPods: MagicAAP](https://magicpods.app/magicaap/)

Route: Android phone
- LibrePods reads AirPods head tracking and gestures on Android, without root only on ColorOS/OxygenOS 16, realme UI 7.0 and Pixel on Android 16 QPR3; elsewhere it needs root plus Xposed. — [LibrePods Android README](https://github.com/librepods-org/librepods/blob/main/android/README.md)

### Inferences
- Recommended order for a Windows 11 developer: (a) to prove the idea in an hour, SmoothTrack to OpenTrack, then read OpenTrack's UDP output or listen on port 4242 in Python; (b) for full fields (quaternion, rotation rate, gravity, user acceleration, `sensorLocation`), an own app: Swift Playgrounds on an iPad (free, no Mac) is the cleanest, and xtool or a cloud runner plus Sideloadly is the iPhone equivalent (free but re-sign weekly); (c) pay $99/year only if you need TestFlight, EAS internal distribution, 1-year profiles or more than 3 test apps.
- EAS simulator builds do not need a paid account, but the simulator returns no headphone motion, so they are useless for this API.
- An Expo project would need a development build with the native module and `ios.infoPlist.NSMotionUsageDescription` in app config; Expo Go cannot load the module (inference from the module needing CocoaPods).
- Keep the data path simple: one JSON or binary UDP datagram per sample (25 to 50 Hz) to the PC's LAN IP, and allow the port through Windows Firewall (airpods-head-tracking warns: "you may need to disable your firewall or allow traffic on port 4242 on your target PC" — [AndressDanylo/airpods-head-tracking](https://github.com/AndressDanylo/airpods-head-tracking)).
- The Windows-only MagicAAP route is the only one with no Apple device, but it is fragile (driver signing, single-consumer driver, firmware-specific packets) and should be a fallback.

### Gaps
- Not checked: the minimum iPadOS version of the current Swift Playgrounds release, and whether Swift Playgrounds apps keep running (and streaming) in the background.
- The Xcode and Apple SDKs licence terms for using the Xcode SDK on non-Apple hardware (relevant to xtool) were not checked.
- Whether SmoothTrack's AirPods mode works with non-Pro models (AirPods 4/5, Max) is not stated in its listing.
- MagicPods/MagicAAP price and current Windows 11 build compatibility were not found.
